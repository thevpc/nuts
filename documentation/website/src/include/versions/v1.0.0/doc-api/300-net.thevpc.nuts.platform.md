<a id="m-NEnv-parallelProcessorRuntimes"></a>

#### parallelProcessorRuntimes

```java
List<NParallelProcessorRuntime> parallelProcessorRuntimes()
```

Parallel processing runtimes available on this environment, each reporting
separately whether code targeting it can be executed and whether it can be
compiled.



This is the software axis, [#gpus()](#m-gpus) being the hardware one. The two
are not interchangeable : a machine holding an NVIDIA device may well
expose cuda as runnable but not buildable, which are opposite answers when
choosing between a prebuilt artifact and sources.

**Returns:**

available runtimes, empty when none is detected

<a id="m-NEnv-refresh"></a>

#### refresh

```java
NEnv refresh()
```

Returns a fresh NEnv instance with current runtime values.



This performs a full re-initialization (may involve SSH commands,
process spawns, etc.) and is significantly more expensive than cached
property access. Use sparingly when environment state is known to have
changed (e.g., after hostname reconfiguration via DHCP).



Existing NEnv instances remain valid snapshots — this returns a NEW
instance. Replace your reference to use the refreshed values:
```java
env = env.refresh();  // ← Must reassign!
```

**Returns:**

new NEnv instance reflecting current environment state

## NGpuDevice

```java
public interface NGpuDevice
```

Represents a GPU hardware device with name, VRAM memory, and capability attributes.

**Author:** thevpc

**Since:** 1.0.0

### Fields

| Modifier and Type | Field | Description |
| :--- | :--- | :--- |
| `String` | `PCI_BUS_ID` | Pci address, as an example 0000:01:00.0. |
| `String` | `PCI_DEVICE_ID` | Raw pci device id, as an example 0x28e1. |
| `String` | `VENDOR` | Hardware vendor, holding an NGpuVendor id such as nvidia. |
| `String` | `DEVICE_TYPE` | Device kind, holding an NGpuDeviceType id such as dedicated-gpu. |
| `String` | `KERNEL_DRIVER` | Kernel module currently bound to the device, as an example nvidia, nouveau or i915. |
| `String` | `DRIVER_VERSION` | Vendor driver version, as an example 580.159.03. |
| `String` | `UUID` | Vendor assigned device uuid. |
| `String` | `COMPUTE_CAPABILITY` | Compute capability as reported by the vendor tool, in the major.minor form such as 8.9. |
| `String` | `PCIE_GEN_CURRENT` | Current pci express link generation, as an example 1. |
| `String` | `PCIE_GEN_MAX` | Highest pci express link generation the device supports. |
| `String` | `PCIE_WIDTH_CURRENT` | Current pci express link width in lanes, as an example 8. |
| `String` | `PCIE_WIDTH_MAX` | Highest pci express link width the device supports, in lanes. |

<a id="m-NGpuVendor-getComputeKernelModule"></a>

#### getComputeKernelModule

```java
public String getComputeKernelModule()
```

Name of the linux kernel module that must be bound to a device for this
vendor's own compute stack to have any chance of driving it.



The module actually bound is the reliable capability gate : an NVIDIA card
driven by `nouveau` is perfectly functional for display yet has no
CUDA capability at all, which happens on fresh installs and whenever
secure boot rejects the proprietary module.



The condition is sufficient for [#NVIDIA](#m-NVIDIA) only, where the module
ships the driver api that CUDA needs. For [#AMD](#m-AMD) it is necessary but
not sufficient, ROCm additionally requires the `/dev/kfd` node and
its userspace. [#INTEL](#m-INTEL) reports none on purpose : `i915` is a
display driver, Intel compute goes through the separate Level Zero
runtime, whose detection is not implemented yet.

**Returns:**

expected kernel module name, or null when the vendor's compute
stack cannot be concluded from a bound module

<a id="cls-net-thevpc-nuts-platform-NParallelProcessorRuntime"></a>

## NParallelProcessorRuntime

```java
public class NParallelProcessorRuntime
```

Availability of a parallel processing runtime on a machine.



The important part is that executing and building are reported separately,
because they are installed separately and lead to opposite decisions. A
machine with an NVIDIA driver but no CUDA toolkit can run a prebuilt cuda
binary yet cannot compile one, while a build container with the toolkit and no
device is exactly the reverse. Reducing both to a single "has cuda" boolean
loses the distinction a resolver needs to choose between shipping a prebuilt
artifact and shipping sources, which is why
[NParallelProcessorFamily#detectAvailable()](#cls-NParallelProcessorFamily) reports them apart.
