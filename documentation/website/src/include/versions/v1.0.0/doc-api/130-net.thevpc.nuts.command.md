# Package net.thevpc.nuts.command

<a id="pkg-net-thevpc-nuts-command"></a>

High-level workspace commands and their execution contracts.



The package defines commands for searching, fetching, deploying, installing,
executing, updating, removing, and inspecting artifacts. It also contains their
options, events, results, status models, and domain-specific failures. Command
implementations operate through an [net.thevpc.nuts.core.NWorkspace](#cls-net-thevpc-nuts-core-NWorkspace) and
repository-side command extensions are defined in `net.thevpc.nuts.spi`.

## NExec

```java
public interface NExec extends NWorkspaceCmd, NConnectionStringAware
```

Represents a command execution within the Nuts workspace.



`NExec` provides a unified API to execute all types of executables:


- Internal commands managed by Nuts
- External executables on the local machine
- System commands using the underlying OS shell
- Remote commands via networked connections (SSH, RSH, etc.)





The command can be configured with:


- Command arguments and executable paths
- Environment variables
- Executor options
- Workspace options (affecting subprocess or embedded execution)
- Standard input/output/error redirection and capturing
- Run-as context (current user, root, sudo)
- Bot mode for clean, machine-readable output
- Remote connection targeting via [#at(String)](#m-at) or [#at(NConnectionString)](#m-at)





Commands can be executed in different modes:


- Embedded execution within the current JVM
- Spawned as a separate process
- System execution using the OS shell
- Opening files or URLs with the associated OS handler





`NExec` supports output grabbing, error redirection, dry-run mode,
and execution target probing (local or remote).



The API is fluent, allowing chaining of configuration calls before execution.



Example usage:
```java
NExec.of("ls", "-l")
        .setBot(true)
        .at("ssh://remote-server")
        .grabOut()
        .run();
String output = cmd.grabbedOut();
```

## NExecutionContext

```java
public interface NExecutionContext extends NSessionProvider
```

Represents the execution context for commands executed via [NExecutorComponent](#cls-NExecutorComponent)
or [NInstallerComponent](#cls-NInstallerComponent). This interface provides all information and
configuration needed to run a command, including arguments, environment,
I/O redirection, execution type, and user context.



The execution context allows:


- Capturing standard output, error, and input streams
- Setting workspace and executor options
- Specifying execution environment and working directory
- Configuring execution flags such as fail-fast, dry-run, bot mode
- Probing remote or local execution targets





Instances of this interface are generally provided by the executor framework
and can be extended or decorated as needed for specific execution requirements.





**Author:** thevpc

**Since:** 0.5.4

### Method Summary

| Modifier and Type | Method | Description |
| :--- | :--- | :--- |
| `String` | [commandName()](#m-NExecutionContext-commandName) | Returns the name of the command being executed. |

## NExecutionType

```java
public enum NExecutionType implements NEnum
```

Specifies the type of command execution.



This enum defines how a command or executable is resolved and run
by the Nuts framework. Each type determines the execution strategy,
whether running in-process, via the OS, or as a document opener.






- [#SPAWN](#m-SPAWN) – Resolves the command as an external artifact or executable.
        Nuts selects the appropriate executor to run it.
- [#SYSTEM](#m-SYSTEM) – Executes a native command using the underlying
        operating system, typically via [ProcessBuilder](#cls-ProcessBuilder).
- [#EMBEDDED](#m-EMBEDDED) – Executes a Java class in the current JVM
        using classloading, without spawning a new process.
- [#OPEN](#m-OPEN) – Opens documents or files using the system's default
        application for the given file type.






Use the appropriate type to control how commands are executed and how
Nuts resolves their environment and dependencies.




**Author:** thevpc

**Since:** 0.5.4

### Enum Constants

| Constant | Description |
| :--- | :--- |
| `SPAWN` | Command will be resolved as an external artifact or executable. |
| `SYSTEM` | Command will be executed as a native system command. |
| `EMBEDDED` | Command will be executed as a Java class within the current JVM. |
| `OPEN` | Command will be treated as a file or document to open. |

<a id="cls-net-thevpc-nuts-command-NFetchMode"></a>

## NFetchMode

```java
public enum NFetchMode implements NEnum
```

fetch mode defines if the artifact should be looked for withing the "installed" meta repository, "local" (offline)
machine repositories or over the wire (remote repositories).



"installed" artifacts are stored in a pseudo-repository called "installed" which include all installed
(using command install) artifacts. Effective storage may (should?) remain in a local repository though.
Actually pseudo-repository "installed" manages references to these storages.




local repositories include all local folder based repositories. Semantically they should define machine/node based
storage that is independent from LAN/WAN/Cloud networks. A local database based repository may be considered as local
though not recommended as the server may be down.
Il all ways, local repositories are considered fast according to fetch/deploy commands.




remote repositories include all non local repositories which may present slow access and connectivity issues.
Typically this include server based repositories (http, ...).




It's important to say that a repository may serve both local and remote artifacts as usually remote repositories
enable cache support; in which case, if the artifact si cached, it will be accessed locally.



**Since:** 0.5.4

<a id="cls-net-thevpc-nuts-command-NSysEditorSupportCmd"></a>

## NSysEditorSupportCmd

```java
public interface NSysEditorSupportCmd extends NCmdLineConfigurable, NComponent
```

Command interface for installing syntax highlighting support across various text editors.



This component enables automatic installation of language syntax definitions to supported
text editors, making it easier for users to work with custom file formats. It supports
major editor families including VSCode, IntelliJ IDEA, Vim, Kate, and others.




<h2>Usage Example</h2>
```java
// Install syntax for all supported editors
NSysEditorSupportCmd.of()
    .setLanguageId("tson")
    .setLanguageName("TSON")
    .setFileExtension(".tson")
    .setSource(NPath.of("classpath:/integration/tson"))
    .addEditorFamilies(NSysEditorFamily.values())
    .run();

// Install for specific editors only
NSysEditorSupportCmd.of()
    .setLanguageId("ntexup")
    .setLanguageName("NTexUp")
    .setFileExtension(".ntx")
    .setSource(NPath.of("/path/to/integration"))
    .addEditorFamily(NSysEditorFamily.VSCODE)
    .addEditorFamily(NSysEditorFamily.VIM)
    .run();
```

<h2>Source Directory Structure</h2>



The source directory should contain subdirectories for each editor family, plus an
optional configuration file that defines language metadata:



```java
integration/
├── sys-editor-support.tson  # Optional: language metadata
├── gedit/
│   └── language.lang
├── jedit/
│   └── language.xml
├── vim/
│   └── language.syntax.vim
│   └── language.ftdetect.vim
├── vscode/
│   ├── language-configuration.json
│   └── language.tmLanguage.json
├── intellij/
│   └── language.xml
├── notepad-plus-plus/
│   └── language.xml
└── kate/
    └── language.xml
```

<h2>Configuration Priority</h2>



Language properties are resolved in the following order (highest to lowest priority):





- **Explicit setters** (`setLanguageId()`, `setFileName()`, etc.) - Always override
- **sys-editor-support.tson** - Values from configuration file
- **Default setters** (`setDefaultLanguageId()`, `setDefaultFileName()`, etc.) - Only used if not already set





Example sys-editor-support.tson:


```java
{
    languageName: "NTexUp",
    languageId: "ntexup",
    languageVersion: "1.0.0",
    languageGroupId: "net.thevpc",
    fileName: "*.ntx",
    fileExtension: ".ntx"
}
```

#### run

```java

```

Executes the syntax installation command.



This method reads the syntax definition files from the configured source path
and installs them to the appropriate configuration directories for each selected
editor family. The installation process:





- Detects which editors are installed on the system
- Creates necessary configuration directories if they don't exist
- Copies syntax definition files to the correct locations
